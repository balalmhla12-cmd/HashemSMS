# HashemSMS — مخطط تصميم جميع الواجهات قبل استكمال الوظائف

التاريخ: 2026-10-21
الفرع: `phase1-ui`
الحزمة المحمية: `com.hashem.sms`

## القرار التنفيذي

تسبق مرحلة التصميم أي مرحلة توسعة وظيفية جديدة. نجهز جردًا وتصميمًا موحدًا لجميع الشاشات والحالات، ثم نراجع التصميم، ثم نربط كل عنصر بوظيفته الموجودة أو نحدد الوظيفة الناقصة، وبعدها نبدأ تحسين قاعدة الربط والاختبارات. هذا المخطط لا يجيز حذف أي ميزة أو تغيير سلوك قائم.

## قواعد ثابتة

- الحفاظ على كل الوظائف الحالية دون حذف أو تعطيل، وعلى package `com.hashem.sms` ولغة Java وRTL.
- الاحتفاظ بهوية HashemSMS والألوان المعتمدة والوضع الفاتح والداكن؛ لا تخمين ألوان جديدة ولا ألوان ثابتة داخل Java.
- تصميم الواجهة لا يعني أن الوظيفة منفذة أو مختبرة. تُوسم كل ميزة بوضوح: موجودة في الكود، تحتاج ربطًا، تحتاج تنفيذًا، أو تحتاج اختبار جهاز.
- عدم تغيير قاعدة البيانات أو الأذونات أو منطق الإرسال في مرحلة التصميم.
- كل تعديل في commit مستقل، ولا انتقال دون نجاح أحدث GitHub Actions. لا تعديل على Lint baseline/limit، ولا دمج إلى main دون موافقة المستخدم.

## قائمة الواجهات التي يجب جردها وتصميمها

### أ. التنقل الأساسي
1. المحادثات: قائمة المحادثات، البحث، فلاتر الكل/غير المقروء/المميزة/المؤرشفة، تحديد متعدد، والقائمة الفارغة.
2. تفاصيل المحادثة: الرسائل الواردة والصادرة، فواصل التاريخ، حالات الإرسال والتسليم والفشل، مربع الكتابة، المرفقات، اختيار الشريحة، وقائمة إجراءات الرسالة.
3. إنشاء محادثة جديدة: البحث عن اسم/رقم، اختيار جهة اتصال، إدخال رقم يدوي، والتحقق من الرقم.
4. جهات الاتصال: القائمة، البحث، الصور الرمزية، تفاصيل جهة الاتصال، والبدء بمحادثة.
5. المزيد: نقطة دخول واضحة إلى كل أدوات الإدارة دون إخفاء أو حذف أي وظيفة قائمة.

### ب. إدارة المحادثات والرسائل
6. المؤرشفة.
7. المحظورة وإدارة الحظر.
8. المهملات، الاستعادة، والحذف النهائي مع تأكيد.
9. الرسائل المميزة بنجمة.
10. الرسائل الفاشلة وتفاصيل الخطأ وإعادة المحاولة/التوجيه.
11. الجدولة: قائمة المجدول، إنشاء/تعديل/إلغاء موعد، وحالات التعذر والاستعادة.
12. الرسائل الجماعية: كتابة المحتوى، اختيار المستلمين، استيراد CSV/نص، معاينة المتغيرات مثل {name}، وتأكيد الإرسال.
13. مجموعات المستلمين: قائمة المجموعات، إنشاء/تعديل، وإدارة الأعضاء.
14. قواعد التوجيه: القائمة، إضافة/تعديل، التفعيل والتعطيل، وشرح واضح قبل تطبيق أي مسار بديل.
15. تحديد متعدد: شريط الإجراءات، التأكيدات، والحالات التي لا ينطبق فيها الإجراء.

### ج. الإعدادات والخصوصية
16. الإعدادات العامة.
17. إعدادات الإشعارات والرد المباشر وتعليم كمقروء.
18. تفضيلات المظهر: فاتح/داكن/حسب النظام، مع RTL.
19. اختيار الشريحة الافتراضية وسلوك الإرسال عند تعدد الشرائح.
20. إعدادات الجدولة.
21. إعدادات الخصوصية/قفل التطبيق إذا تأكدت متطلباته، دون الادعاء بأن الميزة موجودة قبل تنفيذها.
22. معلومات التطبيق والصلاحيات وتعيين التطبيق الافتراضي وحالات سحب الصلاحيات.
23. النسخ الاحتياطي والاستيراد/التصدير كواجهات مستقبلية لا تُعرض على أنها تعمل قبل تنفيذها.

### د. الوسائط والرسائل متعددة الأنواع
24. منتقي الصور/الكاميرا ومعاينة الصورة قبل الإرسال.
25. تسجيل صوتي قصير، تشغيل المعاينة، إعادة التسجيل/الإلغاء، والإرسال.
26. اختيار فيديو ومعاينته وإظهار الحجم/المدة وحدود الناقل.
27. معاينة مرفق عام وحالة التنزيل.
28. تقدم الإرسال/التنزيل، الإلغاء حيث يدعمه المسار، والفشل وإعادة المحاولة.
29. توضيح نوع الإرسال قبل الإرسال: SMS نصي أو MMS أو RCS إن كان متاحًا ومتكاملًا رسميًا؛ تحذير من أن السعر يعتمد على شركة الاتصالات والباقة والحجم، ولا تقدير مالي غير موثوق.

### هـ. الحالات المشتركة لكل الشاشات
30. تحميل/تحديث.
31. لا توجد بيانات.
32. فشل التحميل أو الإرسال مع إجراء مفهوم.
33. رفض الإذن مع تفسير وخيار فتح إعدادات النظام.
34. لا توجد شريحة صالحة/لا توجد خدمة/بيانات الهاتف معطلة.
35. تأكيد العمليات غير القابلة للعكس.
36. دعم حجم الخط وقارئ الشاشة والتباين والتركيز والتنقل.
37. RTL، أسماء/أرقام طويلة، رسائل طويلة، شاشات صغيرة، الوضع الفاتح والداكن.

## تسليم مرحلة التصميم

- مصفوفة شاشة × مكونات × إجراءات × حالات × مصدر البيانات × الاختبارات.
- توحيد مكونات الواجهة المتكررة (شريط العنوان، البحث، الشرائح، البطاقات، الرسائل، القوائم، الحوارات، حالات الفراغ والخطأ).
- توثيق تدفق التنقل بين كل شاشة والشاشة التالية، مع الحفاظ على مسارات الوظائف الموجودة.
- قائمة صريحة بما هو موجود وما هو ناقص؛ لا تُنشأ أزرار وهمية توحي بأن وظائف غير موجودة تعمل.
- مراجعة بصرية على RTL والوضعين الفاتح والداكن قبل أي تغييرات وظيفية واسعة.

## ترتيب التنفيذ بعد التصميم

1. جرد الشاشات والروابط الحالية ومراجعة أحدث CI.
2. إكمال تصميم كل الواجهات والحالات وتوحيد المكونات دون تغيير المنطق.
3. تدقيق طبقة الربط بين الواجهات والبيانات والخدمات، ثم إصلاح الربط الناقص فقط.
4. إكمال الوظائف الناقصة واحدة تلو الأخرى مع اختبارات الانحدار.
5. تنفيذ MMS والمرفقات بعد تدقيق البنية الحالية واختبار دعم الناقل/الشريحة.
6. اختبارات جهاز حقيقي ثم الإصدار النهائي.

## بوابة قبول المرحلة

لا تُقبل مرحلة التصميم إلا بعد توثيق جميع الشاشات والحالات المذكورة، التحقق من عدم حذف أي عنصر وظيفي قائم، نجاح أحدث GitHub Actions، وعدم زيادة تحذيرات Lint عن baseline الحالي (15 وفق آخر سجل ناجح). لا يُعتبر الإرسال الحقيقي أو MMS أو RCS مختبرًا بمجرد نجاح البناء.
